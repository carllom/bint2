Prototype — Bitmap packing: MSB-first, Stride, invert

Ticket “Bitmap rendering: prove the packing function against real font/icon data” (#70), on map #63. The Bitmap renders a contiguous run of the document’s bytes 1 bit per pixel — each byte is eight horizontal pixels, a set bit paints the foreground. Before that render is specced into a milestone, this page pushes the core packing transform through real glyph tables, a padded framebuffer, and edge cases that are hard to check on paper.

The question being prototyped: is the packing function (bytes, width, stride, height, invert) → 1-bit pixel buffer correct against real data — does MSB-first render upright, does Stride > Width skip the right gap bytes, does invert do only what it should, does integer Zoom stay crisp — and does anything here argue for pulling LSB-first or column-major packing out of the map’s fog now rather than later?

Prototype branch: LOGIC (per the prototype skill) — the question is whether a transform is right, not what a UI should look like. But a bitmap can only be judged by looking at it, so “current state” below is a live <canvas> next to the numeric state. Everything is in memory; nothing is persisted.

Already decided — not reopened here (#65, ADR-0008): MSB-first (bit 7 = leftmost pixel), bit value 1 = foreground, invert swaps foreground/background, colours follow the theme (no pickers), Zoom 1–3 with image-rendering: pixelated and smoothing off. This prototype validates those against real bytes and probes the LSB-first / column-major fog — it does not re-litigate them.

The module under test

Everything on the canvas is driven by one throwaway module (bitmap, in this file’s <script>), written as the pure surface the ticket wants to freeze — no DOM, no store:

  • rowByteSpan({width, stride, height}) → stride·(height−1) + width, the byte count a render needs (the read-path ticket #66 pins this).
  • packBitmap(bytes, {width, stride, height, invert, bitOrder, order}) → { bits: Uint8Array (0|1 per pixel), w, h, bytesRead, bytesMissing }. bitOrder defaults to 'msb' and order to 'row' — the other values ('lsb', 'col') are the fog previews, present only so this page can show what they would do.

Colour lives outside the pure module: a throwaway paint() turns bits into ImageData, putImageData onto a 1× canvas, then drawImage upscaled by integer Zoom with smoothing off. If the walkthroughs pass, rowByteSpan + packBitmap lift into src/core/bitmap.ts roughly as-is.
