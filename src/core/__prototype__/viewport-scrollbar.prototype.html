Prototype — viewport.ts scrollbar & coordinate model

Ticket “Scrollbar & coordinate model at ~94 M rows” (#8). The Phase 1 hex viewer has no native scrollbar — the document is up to ~125 M rows, far past every browser’s element-height limit — so scroll position is a pure topByteOffset value and a hand-drawn thumb. This page lets you drive that model by hand at real scale and feel where it breaks.

The question being prototyped: at multi-GB scale one thumb-pixel is hundreds of thousands of rows, so dragging the thumb can never land on a chosen offset. Is that acceptable because wheel + keyboard + Goto carry all the fine movement (confirm §11), or does Phase 1 need the two-level “zoom” scrollbar that §12 floats? And does the pure-function surface below survive the awkward cases well enough to freeze it for viewport.ts?

Already settled, not in scope here: part (a) “custom thumb vs. hybrid native scrollbar below a size threshold” was closed by “Max file-size target for phase 1” (#2) — the custom VirtualScrollbar is the only scrollbar at every file size, no native fallback, no hybrid. This prototype only exercises the custom model.

The model under test

Everything below is driven by one throwaway module (Viewport, in this file’s <script>) written as the pure-function set the ticket wants to freeze: rowOfOffset, offsetOfRow, rowCount, visibleRows, maxFirstRow, clampTopOffset, thumbGeometry, offsetFromThumbPixel, plus the bytesPerRow-change offset rule. If the walkthroughs pass, this surface lifts into src/core/viewport.ts unchanged.
